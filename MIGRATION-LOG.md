FINDING: One malformed access rule in Redis makes every lookup that matches it return no rules at all
- What is wrong: `parseRedisRecords` in `packages/user-access-policy/src/redis/redisClient.ts` is meant to skip a record that fails to parse and keep the rest (it uses `safeParse` and logs the failure). But `accessRuleInput` (`src/ruleInput/ruleInput.ts`) has transforms that throw rather than report an issue: `userIpInput` in `src/ruleInput/userScopeInput.ts` calls `getIPAddress`, which throws `API.INVALID_IP` or `AddressError`, and the `numericIp*` fields call `BigInt()`, which throws `SyntaxError`. A throw inside a zod transform escapes `safeParse`, so the whole `flatMap` aborts. The callers in `src/redis/reader/redisRulesReader.ts` (`findRules`, and the paths at lines 388, 503, 564) catch it and return `[]`.
- Evidence, reproduced: `parseRedisRecords([good, bad, good], accessRuleInput, logger)` run with tsx on Node 24, where `good` is `{type:"block",clientId:"a"}`: with `bad` = `{type:"block",numericIp:"abc"}` it threw `SyntaxError: Cannot convert abc to a BigInt`; with `{type:"block",ip:"999.1.1.1"}` it threw `Error: API.INVALID_IP`; with `{type:"block",ipMask:"1.2.3.4/99"}` it threw `AddressError: Incorrect number of groups found`. In none of the three were the two good records returned.
- Impact: this fails open. Every request whose lookup matches the bad record gets no block or restrict rule, including from the other, valid rules in the same result. The writer (`RedisRulesWriter`) only stores values that already passed these transforms, so a bad record can only come from something else writing `uar:*` hashes: a manual `HSET`, an older writer, or a private-repo job writing Redis directly. No such record is known to exist in production. The same throw also makes an admin API body with such a value fail with a 500 rather than a 400.
- What I would do: make those transforms report a zod issue (`ctx.addIssue` then `z.NEVER`) instead of throwing, so the bad record is skipped and logged as intended, and the API answers 400. Nothing stored changes and no migration is needed. The Rust port already behaves this way (logged as a DEVIATION on the user-access-policy line).

FINDING: Admin rule filters on groupId, webBotAuthAgent or header fields silently match nothing when the value contains `-`, `.`, `:` or `/`
- What is wrong: the RediSearch query builders in `packages/user-access-policy/src/redis/reader/redisRulesQuery.ts` and `redisRulesSplitQuery.ts` escape only the `coords` TAG value. Every other TAG value is put into `@field:{value}` as is, and RediSearch treats `-`, `.`, `:` and `/` in a TAG query as syntax.
- Evidence, reproduced on Redis Stack 7.4.0-v8 (RediSearch 2.10.20, the image production runs) by an earlier session: `FT.SEARCH` with `@clientId:{client-a}` and with `@webBotAuthAgent:{https://signatures.openai.com}` both fail with a syntax error. The reader catches the error and returns no rules.
- Impact: the request path is not affected, because the values it queries (SS58 client ids, ja4 fingerprints, hashes, country codes, OS and browser names) never contain those characters. The admin endpoints are: `find-ids` and `delete-many` filtered on `groupId`, `webBotAuthAgent` or a header field with such a value return nothing and delete nothing, with no error to the caller. Any `webBotAuthAgent` rule is affected, because its value is always a URL.
- What I would do: run every TAG value through the existing escape function in both query builders, in the TS and the Rust together. Nothing stored changes and no migration is needed. One behaviour change to announce: admin deletes by those filters would start deleting rules they currently miss.

FINDING: insertRules returns the wrong rule ids: it drops the first four ids of every batch and leaves the rest prefixed
- What is wrong: `RedisRulesWriter.insertRules` in `packages/user-access-policy/src/redis/redisRulesWriter.ts` (line 46) does `keyBatches.flatMap((ruleKey) => ruleKey.slice(ACCESS_RULE_REDIS_KEY_PREFIX.length))`. `keyBatches` is `string[][]` (one array of keys per batch), so `slice(4)` acts on each batch array, not on a key. It removes the first four keys of every batch and leaves every remaining key with its `uar:` prefix. TypeScript accepts it because `string[].slice` also returns `string[]`.
- Evidence: confirmed by reading the code and the types. The Rust port's equivalence vectors, generated by running the TS, record the TS output, and the Rust deliberately differs (DEVIATION (1) on the user-access-policy line).
- Impact: small. The rules themselves are written correctly. Only the return value is wrong: the insert endpoint (`src/api/write/insertRules.ts`) logs `insertedCount`, `uniqueIdsCount` and `insertedIds` from it, so those log fields are wrong for every insert; `rehashRules` ignores the value. No API response or stored record carries it.
- What I would do: `keyBatches.flat().map((key) => key.slice(ACCESS_RULE_REDIS_KEY_PREFIX.length))`. No migration.

FINDING: PowChallengeIdSchema accepts any string with four `___`-separated parts, because its number check can never fail
- What is wrong: `PowChallengeIdSchema` in `packages/types/src/datasets/captcha.ts` (line 156) wraps `Number.parseInt(valSplit[0])` in `try`/`catch` to reject a non-numeric timestamp, but `parseInt` never throws (it returns `NaN`), so the check does nothing and only the part count is tested. Separately, the function calls `val.split` before checking that `val` is a string, so a non-string throws a `TypeError` out of `safeParse` instead of failing validation.
- Evidence, reproduced with tsx on Node 24: `safeParse("x___y___z___w")` and `safeParse("1___2___3___4")` are both accepted, `safeParse("a___b")` is rejected, `safeParse(5)` throws `TypeError: val.split is not a function`, and `safeParse(null)` throws `TypeError: Cannot read properties of null (reading 'split')`. (An earlier note in this log said the throw becomes a 500. It does not on the one request path: `submitPoWCaptchaSolution` catches every parse error and answers 400 `CAPTCHA.PARSE_ERROR`.)
- Impact: none found on the request path. A forged challenge id that passes the schema still has to match a stored PoW record, which it will not. The schema is also used for stored PoW records (`packages/types/src/provider/database.ts`, line 794), where it validates nothing beyond the part count.
- What I would do: check `typeof val === "string"` first, and test the first part with `/^\d+$/` (or `Number.isSafeInteger(Number(part))`). That could reject a stored record or a request that passes today only if its timestamp part is not a number, which nothing writes. No migration.

FINDING: PublicProsopoServer can never verify a token

FINDING: Open question: should a malformed Signature-Agent header give a 400 on the frictionless challenge instead of being treated as unsigned?
- What is wrong: `verifyWebBotAuth` in `packages/web-bot-auth/src/verify.ts` returns a failure reason for every bad input except two, which throw: a `Signature-Agent` URL that the header regex accepts but `new URL` rejects (`normaliseSignatureAgentUrl` in `src/parseSignatureAgent.ts`), and a `null` entry in the JWKS before the matching key. The caller, the frictionless challenge handler (`packages/provider/src/api/captcha/getFrictionlessCaptchaChallenge/handler.ts`, line 634), does not catch it, so the request falls through to the handler's outer `catch` and is answered with `API.BAD_REQUEST` (400).
- Evidence, reproduced: tsx on Node 24, `verifyWebBotAuth` with `signature-agent: "https://[x"` and otherwise valid headers threw `TypeError: Invalid URL`. The outer `catch` at line 1012 of the handler wraps any error as a 400.
- Impact: only clients that send Web Bot Auth headers, which browsers do not. This fails closed, so it is not a security hole; it is an inconsistency, and the question is which behaviour is intended.
- What I would do, if the answer is "treat it as unsigned": wrap the two throwing calls and return `unparseable-signature-agent` and `malformed-key`. The Rust port keeps the throw until the owner decides.

FINDING: KeyringPair.vrfVerify ignores its signerPublic argument
